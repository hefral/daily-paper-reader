## 摘要
随着机器人控制转向具有回路内动力学计算的大规模强化学习，社区对Pinocchio等受CPU限制的库的依赖在基于GPU的训练流程中造成了吞吐量瓶颈。我们提出了BARD（批量铰接刚体动力学），一个自包含的PyTorch实现，基于Featherstone的刚体动力学算法，针对批量GPU评估和自动微分进行了优化。三个设计选择使其高效：分层惰性求值缓存避免了冗余树遍历，通过预计算的罗德里格斯常数实现的免矩阵乘法关节变换，以及层次并行传播将顺序操作减少到树深度级别的批量步骤。在五个机器人模型（7-23自由度）上，BARD在数值上与Pinocchio匹配，同时在NVIDIA H200上以批量大小4096进行正向运动学计算时吞吐量最高提升64倍，雅可比矩阵计算提升63倍。我们通过在7自由度机械臂上进行基于梯度的系统辨识验证了可微分性，在5％扭矩噪声下恢复的连杆质量平均误差为1.24％，并将BARD集成到Isaac Lab的AMP训练流程中，用于具有4096个并行环境的11自由度带脊柱四足机器人，其中回路内动力学比Pinocchio快8.5倍，比ADAM快2.0倍。BARD已在以下地址开源：https://github.com/YueWang996/bard-pytorch-dynamics。

## Abstract
As robot control shifts toward large-scale reinforcement learning with in-loop dynamics computation, the community's reliance on CPU-bound libraries such as Pinocchio creates a throughput bottleneck in GPU-based training pipelines. We present BARD (Batched Articulated Rigid-body Dynamics), a self-contained PyTorch implementation of Featherstone's rigid-body dynamics algorithms, optimized for batched GPU evaluation and automatic differentiation. Three design choices make this efficient: a tiered lazy-evaluation cache that avoids redundant tree traversals, matmul-free joint transforms via pre-computed Rodrigues constants, and level-parallel propagation that reduces sequential operations to tree-depth batched steps. On five robot models (7-23 DOFs), BARD matches Pinocchio numerically while reaching up to 64x higher throughput for Forward Kinematics and 63x for Jacobians at batch size 4096 on an NVIDIA H200. We validate differentiability through gradient-based system identification on a 7-DOF manipulator, recovering link masses to 1.24% mean error under 5% torque noise, and integrate BARD into an Isaac Lab AMP training pipeline for an 11-DOF spined quadruped with 4096 parallel environments, where it is 8.5x faster than Pinocchio and 2.0x faster than ADAM for in-loop dynamics. BARD is open-sourced at: https://github.com/YueWang996/bard-pytorch-dynamics.

- **核心问题**：机器人控制越来越多地依赖大规模强化学习（RL），训练时需要在回路中反复计算刚体动力学（如前向运动学、雅可比、逆动力学等）。然而，社区常用的动力学库 **Pinocchio** 是 CPU 串行实现，每次调用都需要 CPU‑GPU 数据传输，成为 GPU 训练流程中的严重吞吐瓶颈。
- **现有方法的不足**：GPU 仿真器（如 Brax、MuJoCo MJX）虽具高吞吐，但多为整体式模拟器，难以抽取独立的动力学算子嵌入自定义损失或控制器；基于 JAX 的库又难以原生集成到 PyTorch 训练栈。已有的 PyTorch 动力学库（ADAM）因追求后端通用性而牺牲了 GPU 利用率，且均未针对 `torch.compile` 进行设计。
- **工作定位**：本文提出 **BARD**（Batched Articulated Rigid‑body Dynamics），一个纯 PyTorch 实现的 Featherstone 刚体动力学算法库，专为批量 GPU 评估和自动微分优化，旨在填补 GPU 原生、高性能、模块化动力学工具的空缺。

## 2. 方法论

BARD 以 Featherstone 的空间向量算法为基础，通过以下四项关键技术实现高效批量 GPU 计算：

- **分层惰性求值缓存**
  - 将运动学状态分为三个惰性层：① 局部父子变换 `Tpc,i`；② 空间伴随变换 `Xup,i`、`Si`；③ 世界坐标系位姿 `0Ti`。
  - 每个层由有效性标志控制，仅在下游算法首次请求时才计算，避免无用计算（例如仅调用 RNEA 时不计算世界位姿传播）。

- **免矩阵乘法的关节变换**
  - 转动关节的父子变换涉及两次 4×4 矩阵乘法，对于 GPU 上数千个小矩阵乘法，启动开销远大于算术成本。
  - 通过预计算固定几何偏移对应的 Rodrigues 常数（公式 (2)–(3)），运行时仅用 sin(q) 和 cos(q) 做标量-矩阵乘法和加法（公式 (4)–(5)），将全部关节和批次融合为单个内核启动。

- **按层并行的树传播**
  - Featherstone 算法的父→子（或子→父）遍历本来串行。BARD 在构建时预计算**层次顺序分组**，将同一深度的所有节点作为一次批量操作并行计算，例如前向速度传播变成 `v[ℓ] = Xup,[ℓ] · v_parent(ℓ) + S[ℓ] · q̇[ℓ]`。
  - 将 `nb` 次串行步骤减少为 `树深度` 次批量步骤。反向累积仍保持拓扑顺序，但所有 `B` 个环境同时处理。

- **直接构造雅可比列**
  - 对于单自由度关节，不构造完整的 6×6 伴随变换再乘运动子空间，而是利用 FK 缓存直接计算列：`Jk = [(p_wk × R_wk â′_k) ; (R_wk â′_k)]`，省去伴随变换开销。

- **内存布局与编译器兼容性**
  - 所有工作区张量采用 `(B, nb, …)` 布局以保证合并内存访问。
  - 对 CRBA/ABA 中瓶颈的 6×6 更新 `Out += X_i^T M_i X_i`，提供了可选的自定义 Triton 融合内核。
  - 完全兼容 `torch.compile`：树元数据以常量索引张量存储，控制流全部静态，无数据依赖分支。

- **数值保真**：BARD 与 Pinocchio 的最大偏差在 FK/雅可比上接近机器精度（~10⁻¹⁶），动力学算法在 10⁻¹³ 以下，ABA 最大误差约 10⁻¹⁰，满足实际需求。

- **RL 训练实用加速**：在 4096 环境的 AMP 训练中，BARD 比 Pinocchio 快 8.5 倍，比 ADAM 快 2.0 倍，且输出扭矩数值一致，为即插即用替代品。
- **编译策略需谨慎**：`torch.compile` 对运动学有益，但在低带宽 GPU（如 L4）上可能因寄存器溢出导致动力学算法性能下降，建议按需启用。

## 7. 优点

- **完全 PyTorch 原生**：纯 Python/PyTorch 实现，可无缝嵌入现有训练流程，同时支持 `torch.compile` 和自动微分（无需手动推导梯度）。
- **系统级优化新颖**：分层惰性缓存、免矩阵乘的 Rodrigues 常数预计算、按层并行传播等设计显著减少计算冗余和内核启动开销，直接针对 GPU 批量计算的弱点。
- **开源且易用**：URDF 解析 + 预分配工作区，API 简洁，已集成到 Isaac Lab，生态门槛低。
- **实验严谨**：多模型、多算法、多硬件验证，附有详细的附录基准和 `torch.compile` 回归分析，提供了使用建议。

## 8. 不足与局限

- **动力学加速比相对有限**：与运动学 64 倍相比，RNEA/CRBA/ABA 仅 3‑7 倍，因串行反向遍历仍占主导。对于动力学占比较高的任务，收益会缩小。
- **小模型或小批量优势下降**：RL 实验中在 4096 环境下相对 ADAM 仅 2 倍加速（因 spine 控制器仅小部分关节使用动力学），批量或 DOF 较小时内核启动开销会占比增大。
- **`torch.compile` 在低端 GPU 上的退化**：L4 等低带宽 GPU 上动力学算法经编译后可能比 eager 模式慢数倍，用户需要额外 profiling，不是“开箱即最优”。
- **未覆盖接触动力学**：目前仅包含刚体关节空间算法，无接触模型，限制了在需要碰撞响应等任务中的直接应用。
- **RL 训练场景单一**：仅在一个四足机器人和 AMP 任务上展示，缺乏更多类型的控制器或任务验证。
